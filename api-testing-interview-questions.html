Top 10 API Testing Interview Questions and Answers (2026)

API testing checks the services behind the user interface, so it often finds bugs earlier and runs faster than UI tests. Interviewers usually ask about HTTP methods, status codes, authentication, and how you decide what to assert. These answers explain the reasoning behind each choice, so you can describe how you would test a real endpoint.

1. What is API testing?

API testing checks that an application's interfaces work correctly without going through the user interface. It verifies the request and response, status codes, data accuracy, error handling, performance, and security. Because it skips the UI, it runs faster and fails more clearly than an end-to-end test of the same logic.

Why it matters in an interview: interviewers ask this to see whether you can test the business logic directly, not only through screens.

2. What is the difference between REST and SOAP?

REST uses standard HTTP methods and usually exchanges JSON, so it is lightweight and easy to read. SOAP uses XML messages with a formal contract described by WSDL, and it defines its own security and transaction standards. Most new public APIs are REST, while SOAP is still common in banking and older enterprise systems.

Why it matters in an interview: naming where each is still used shows you have worked with real systems, not just the textbook difference.

3. What are the common HTTP methods?

GET reads a resource and should not change data. POST creates a new resource, and PUT replaces an existing one. PATCH updates only some fields, and DELETE removes a resource. Knowing which methods should be safe or idempotent helps you decide what to retry and what to assert.

Why it matters in an interview: the idempotent point is what separates a tester who checks methods carefully from one who only checks the status code.

4. What is a status code?

A status code is the server's summary of the result of a request. 2xx means success, 3xx means a redirect, 4xx means the client sent something wrong, and 5xx means the server failed. A test should check the exact code it expects, not just that the response is not an error.

Why it matters in an interview: asserting the exact code, not a range, catches bugs that a loose check would let through.

5. What is the difference between 200 and 201?

200 OK means the request succeeded and the response body contains the result. 201 Created means a new resource was created, usually after a POST, and the response often includes a Location header with the new resource's address. Asserting 201 rather than 200 confirms the resource was actually created.

Why it matters in an interview: this question tests whether you check what a request did, not only that it returned without an error.

6. What is the difference between authentication and authorization?

Authentication confirms who the caller is, for example by checking a password or a token. Authorization decides what that caller is allowed to do, such as whether a regular user can delete another user's record. A good test suite checks both, including the case where a valid user is refused an action they should not have.

Why it matters in an interview: testing the refusal case is a common gap, and naming it shows security awareness.

7. What is a Bearer token?

A Bearer token is a credential sent in the Authorization header as Authorization: Bearer followed by the token. The server accepts whoever holds the token, so it must be sent only over HTTPS and kept out of logs. Tokens are often JWTs, which can be checked for expiry and signature.

Why it matters in an interview: knowing that a token grants access to anyone who holds it explains why HTTPS and log hygiene matter.

8. What is the difference between PUT and PATCH?

PUT replaces the whole resource, so fields you leave out may be cleared or reset to defaults. PATCH changes only the fields you send and leaves the rest as they are. When testing, send a partial body to PATCH and check that the other fields did not change.

Why it matters in an interview: this is a common bug source, and a test that checks the untouched fields is the strongest answer.

9. How do you test an API?

Start by reading the specification and listing each endpoint, its inputs, and its expected outputs. Send valid requests and check the status code, response body, headers, and response time. Then send invalid input, missing fields, and wrong credentials, and confirm the API returns clear errors without leaking internal details.

Why it matters in an interview: interviewers want a method, not a tool name, so describe the steps in order.

10. What is API contract testing?

Contract testing checks that the request and response shape agreed between a consumer and a provider still matches. The provider is tested against the consumer's expectations, so a change that would break a client fails the build early. It is useful in microservice systems, where many teams deploy independently.

Why it matters in an interview: naming a microservice problem it solves shows you understand where it fits, not just what it is.
